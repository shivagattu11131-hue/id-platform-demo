How to Use

Any service can discover available OIDC clients via this endpoint. Use it to:
- Verify your client is registered before starting the OIDC flow
- List all services that share the same ID Platform
- Debug OIDC integration issues

Dynamic Client Registration (RFC 7591)

POST /oauth2/register - Register a new OIDC client without restarting the ID Platform

New services can call this endpoint to get a client_id and client_secret, then use the standard OIDC Authorization Code flow.

Client credentials will appear here. Save the client_secret - it is shown only once.

How to Onboard a New Service

1. Register your service above (or via POST /oauth2/register)
2. Use the returned client_id + client_secret in your OIDC library
3. Point your OIDC library to the discovery endpoint: http://localhost:3000/.well-known/openid-configuration
4. Implement the Authorization Code + PKCE flow in your service
5. Users can now login once on any service and access all registered services (SSO)

System Architecture

Architecture evolution from two independent auth systems to a unified OIDC-based ID Platform.

Before Migration

Two e-commerce sites with independent authentication systems. No shared identity, no SSO, duplicated user management.

Main Site (Port 3001)

3M customers, ~100M yen/day revenue
SHA-256 + salt password hashing
SQLite database
Username + password auth

MA Site (Port 3002)

100K members, 20K MAU
Plain MD5 password hashing
SQLite database
Username + password auth

During Migration (Phases 0-2)

ID Platform runs alongside both legacy sites. Users are imported, credentials are validated in shadow mode, and new writes are synchronized to both databases.

After Cutover (Phase 3+)

All authentication is handled by the ID Platform via OIDC. Users get Single Sign-On across both sites. Legacy databases are kept in sync.

Migration Plan: 5 Phases

A zero-downtime, zero-password-reset migration strategy designed for safety and reversibility.

Phase 0: Bulk Import

User impact: None. No user-facing changes.

Fetches all users from both legacy sites and imports them into the ID Platform. Password hashes are preserved in their original format (SHA-256+salt, MD5, or BCrypt). Email conflicts between sites are resolved via merge (same email on both sites = one unified account). Each user is tagged with their source site for tracking.

Phase 1: Shadow Mode

User impact: None. Can run for days/weeks to build confidence.

Every login attempt is validated against both the legacy system and the ID Platform. Results are compared to verify password migration accuracy. This phase validates that the ID Platform can authenticate all existing users correctly before any switchover. Runs in parallel with zero user impact.

Phase 2: Dual-Write

User impact: None. Users see no difference.

New registrations and profile updates write to both the ID Platform and the legacy database simultaneously. This ensures both systems stay in sync while the legacy site still handles authentication. If cutover is rolled back, the legacy database has all the latest data.

Phase 3: Cutover + SSO

User impact: Auth switches to ID Platform. SSO enabled.

MA Site (smaller, lower risk) is cut over first, then Main Site. Both sites redirect login to the ID Platform via OIDC (Authorization Code + PKCE). Password hashes that aren't BCrypt are lazily upgraded on first successful login — no forced password resets. Users can now SSO between both sites with one login.

Phase 4: Rollback

User impact: None when rolling back. Auth reverts to legacy.

If problems occur after cutover, rollback reverts auth to the legacy systems. Password changes made during the ID Platform phase are reverse-synced to the legacy database — no user data is lost. Dual-write data is preserved for future re-attempt. Zero data loss, zero confusion.

Security Measures

Password Strategy

BCrypt: Used natively by the ID Platform
SHA-256 + salt: Migrated as-is, verified in shadow mode
Plain MD5: Migrated as-is, lazily upgraded to BCrypt on first login
No forced resets: Users keep their existing passwords

OIDC Security

PKCE (S256): Authorization code interception protection
RS256: Asymmetric JWT signing (JWKS endpoint)
Token validation: Zero-trust filter on all protected endpoints
Session cookies: IDP session for SSO across services

Rollback Safety

Reverse-sync: Password changes made while using the ID Platform are written back to the legacy database during rollback.
Zero data loss: Dual-write data is preserved in both systems throughout the migration.
Minimal risk: Rollback reverts to the exact state before cutover. Users who changed passwords during the IDP phase can still log in via legacy auth.
Re-attempt ready: All migration data is preserved, allowing the team to diagnose issues and re-attempt cutover with fixes.

Each phase requires stakeholder sign-off before proceeding.
Phase 0→1: All users imported, 3 hash formats working
Phase 1→2: ≥99.9% shadow match rate, 2+ weeks observation
Phase 2→3: ≥99.99% sync accuracy, load test passed
Phase 3→4: ≤0.1% login failure, SSO working, rollback drill complete
